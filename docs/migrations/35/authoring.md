# Authoring repository content

Save publication-ready files and original assets, validate, commit, then deploy a
successful static build. There is no database, CMS editor, required `.env`, draft
flag or synchronizer. This repository is public, including Git history: keep
private notes, credentials and unpublished material outside it.

The field definitions live in `src/content.config.ts`; route/reference validation
also runs when pages build. The examples below are templates, not additional
published entries. Final migration verification is tracked [separately](README.md).

## Likes

Create `src/content/likes/<explicit-slug>/index.md`. Use JSON inside the `---`
frontmatter fences, as the imported entries do. JSON strings keep timestamp
precision, whitespace and literal text unambiguous; escape line breaks as `\n`
and embedded quotes as `\"`.

```md
---
{
  "id": "example-find-2026",
  "slug": "example-find",
  "title": "An interesting find",
  "url": "https://example.com/",
  "description": "A literal summary, not Markdown.",
  "commentary": "",
  "type": "",
  "body": "",
  "attribution": "",
  "created": "2026-11-07T12:00:00Z",
  "collections": []
}
---
```

- Choose a unique, stable `id` and an explicit URL-safe lowercase hyphenated
  `slug`. Keep the folder and slug aligned. Imported IDs preserve legacy
  `/likes/<id>` redirects; readable URLs are `/likes/<slug>`. Do not change either
  identity when editing a title, and do not use another item's ID as a slug.
- `created` is the **date added**, not the last edit date. Set it once with a
  timezone. Keep imported `created` and `updated` strings exactly as captured.
  `updated` is optional for new entries and needs no routine manual maintenance;
  neither it nor Git/file timestamps determines Likes chronology.
- Ordinary collection items use `type: ""`, a title, and a destination URL or
  local asset. `type: "quote"` and `type: "note"` use a nonempty literal `body`
  and no asset; quotes can include `attribution`. These are not Markdown bodies.
- `description`, `commentary`, `body`, `attribution` and titles retain literal
  interpretation. Do not move these strings into the Markdown document body or
  add markup expecting it to render.
- For an image, copy the actual source beside `index.md` and add, for example,
  `"image": "./image.jpg"`. Use its real format/extension, not a renamed encoding.
  For a PDF, use `"download": "./document.pdf"` instead. Do not specify both.
  The Likes download publication path must emit PDFs into the built site;
  verify the resulting download, because arbitrary files in `src/` are not
  automatically public. The initial #35 capture contains images, not PDFs.
- Optional `imageVariants: ["./image-320.webp", "./image-640.webp"]` retains
  already optimized, entry-relative images without re-encoding. Two migrated
  items use this to preserve exact deployed pixels. Native `image()` validates
  these assets; other widths are generated by Astro. Variants must have unique
  supported widths and match the primary image's proportions. When replacing
  the primary image, replace or remove its variants too—these are explicit
  authored assets, not an automatically synchronized cache.
- Do not add old asset filenames, `publishedAsset`, transport paths or generated
  responsive-image metadata to frontmatter. Astro owns new image output.

### Named collections

`src/content/named-collections.json` is an array of `{ "id": "stable-id", "name":
"Visible name" }`. Add a registry entry before referencing its ID in a collection
item's `collections` array. Multiple memberships are supported; `[]` leaves the
item ungrouped under “Misc.”. Named collections display alphabetically, items are
newest-first by date added, and empty groups are hidden.

The `misc` ID is reserved for the ungrouped row. Duplicate registry IDs fail validation.
Rename a group by changing its registry `name`, not its ID or every member.
Before removing a registry entry, remove its membership references. Removing a
group does not itself delete its collection items.

## Music

Create `src/content/music/<explicit-slug>/index.md` and place source artwork beside
it. Keep music text in structured frontmatter rather than a Markdown body.

```md
---
{
  "id": "example-release-2026",
  "slug": "example-release",
  "order": 36,
  "category": "graham-van-pelt",
  "artwork": "./artwork.jpg",
  "title": "Example Release",
  "artist": "Graham Van Pelt",
  "release_date": "2026-11",
  "about": "Literal release description.",
  "tracks": [
    { "title": "First track", "track_num": 1 }
  ]
}
---
```

- `id` and `slug` are unique stable identities; `/music/<slug>` must survive title
  changes. Use a category ID from `src/config/site-settings.json`:
  `graham-van-pelt`, `miracle-fortress`, `think-about-life`, or `other-credits`.
- Preserve `release_date` as a string with its original precision. Year-only
  (`"2007"`), year-month (`"2009-10"`), full dates and imported RFC/ISO timestamps
  must not be replaced with invented dates. `display_date` overrides visible
  wording without changing the chronology; `display_title` overrides presentation
  without changing identity.
- `order` is an explicit integer tie-breaker, not filesystem enumeration. Imported
  values 0–35 record deployed global order. Keep their relative order; for a new
  equal-date release, choose its intended position deliberately rather than
  silently reordering existing ties. Categories and dates remain the primary
  grouping/sorting criteria.
- Preserve the `tracks` array's intended order and `track_num` values. `duration`
  is optional and measured in seconds. Optional `audio_url` values use existing
  `/audio/...mp3` paths backed by `public/audio/`; there is no migration-driven
  audio relocation. New local audio must be committed and its emitted URL tested.
- Optional fields include `credit`, `display_title`, `display_date`, `album_id`
  (Bandcamp), `player_height`, `youtube_video_id`, `url`, and `streaming` links
  (`spotify`, `apple`, `tidal`). Preserve fields that apply; do not invent values
  merely to fill a template. `about` may be null, and tracks may be empty.
- Source `artwork` is entry-relative. Optional `artworkVariants` works like Likes'
  `imageVariants`; Paul Cries retains one captured 320px variant. Replace or
  remove variants together with a changed primary artwork. Do not put legacy
  published artwork metadata or hashed compatibility URLs in place of source images.

## Existing software and blog

Software stays in `src/content/software/<slug>/index.mdx` with its existing
structured fields and adjacent images, commonly in `assets/`. Do not enable the
currently unused software MDX bodies as part of editing migrated content.
See [software fields](../../backend-api.md#software-remains-unchanged).

Blog remains MDX under `src/content/blog/`, with a `title` and a quoted
`YYYY-MM-DD` `date` in frontmatter; its filename supplies the route. Unlike Likes
and music literal fields, blog bodies deliberately render Markdown/MDX. Import
components only in posts that use them.

## Validate and publish

```sh
pnpm install
pnpm dev
# Stop the dev server before running build/browser suites.
pnpm check
PLAYWRIGHT_CHROMIUM_EXECUTABLE=/absolute/path/to/working/chromium pnpm test
pnpm build
pnpm preview
```

No publishing environment variables are needed. Review validation failures for
invalid fields, duplicate/conflicting identities or routes, missing named
collections/categories, and missing images/downloads/audio. Do not bypass an error
by dropping an entry or substituting a historical fixture. Inspect preview routes,
media, keyboard/focus interaction and mobile layout. Browser prerequisites must
work; skipped tests are not verification. Run these commands serially, not in a
workspace simultaneously being built by another session.

Commit content and assets together. A successful local build or commit does not
publish anything; manually deploy the successful static build only with owner
approval. Deleting an entry removes it on the next successful deployment, so
review incoming URLs before removal. Keep immutable files under
`public/published-content/` and `public/published-releases/` even when native image
URLs change. Failed builds leave the existing static deployment intact.
